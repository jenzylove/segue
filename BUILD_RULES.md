# Build Rules — Segue

These rules are mandatory for this repository.

## 1. Read before changing
Before every material milestone:
- inspect the repository tree;
- inspect recent commits;
- read `PRD.md`, this file, and `AGENTS.md`;
- read current milestone status/evidence;
- identify what is implemented versus only planned.

Do not rediscover the product from scratch.

## 2. The PRD is the product contract
Do not silently change the product thesis, core loop, locked providers, asset model, user-authority model, or definition of done.

A difficult implementation is not permission to change architecture. Architecture can change only after new verified evidence proves a real blocker, and the PRD must record the decision.

## 3. No throwaway spike phase
Research first, then implement the intended architecture.

Small experiments inside a milestone are allowed, but they do not become a separate multi-day product phase. If an experiment proves useful, fold it directly into production code.

## 4. Outcome-based milestones only
Every milestone must state:
- required outcome;
- affected files;
- external dependencies;
- verification method;
- stop condition.

Do not begin the next milestone until the current stop condition passes or is explicitly blocked.

## 5. Push after every milestone
At each milestone:
1. implement;
2. test;
3. verify the real integrations required by that milestone;
4. update PRD milestone status/evidence;
5. commit with a meaningful message;
6. push;
7. report the exact commit SHA.

No giant uncommitted multi-day worktree.

## 6. Audit PRD after every push
After pushing:
- compare HEAD to `PRD.md`;
- identify planned items not yet implemented;
- identify accidental scope additions;
- update statuses/evidence;
- do not silently remove difficult requirements.

## 7. Backend before polish
Do not redesign or polish the main frontend before:
- contracts pass tests;
- a real Base mainnet B20 buy succeeds;
- a real Base mainnet B20 sell succeeds;
- the worker can advance a policy autonomously.

A beautiful UI around an unproved trading path is not progress.

## 8. No fake integrations
Production code must not use:
- hardcoded fake stock prices;
- fake quotes;
- fake transactions;
- local arrays pretending to be chain state;
- fake worker executions;
- synthetic transaction hashes presented as live.

Mocks are allowed in automated tests only.

## 9. Real data has named provenance
- B20 tokens: Base official verified list.
- trigger/value prices: official Chainlink total-return feeds.
- executable routing: 0x.
- onchain state: Base RPC/contracts.
- chart context: real external market data, clearly labelled.

Never invent an identifier or address.

## 10. Chain is source of truth
Policies, active steps, completion state, balances, and execution evidence must be recoverable from chain.

PostgreSQL and localStorage may cache/label state, but cannot determine whether a real onchain policy exists.

## 11. Worker has bounded authority
The automation wallet:
- pays gas;
- attempts execution;
- never holds user strategy funds;
- cannot withdraw from user vaults;
- cannot change rule parameters;
- cannot execute a wrong token pair;
- cannot exceed per-step or total limits.

The contract must revalidate the condition at execution time.

## 12. Secrets never enter Git
Never commit:
- private keys;
- 0x API keys;
- private RPC URLs/tokens;
- database passwords;
- deployment credentials.

Use `.env` locally and platform secret stores in deployment. `.env.example` contains names only.

## 13. Builder Code from the start
Base transactions generated by Segue that support attribution must carry the project's ERC-8021 Builder Code from the beginning of the real evidence phase.

## 14. Mainnet claims require mainnet evidence
Keep statuses separate:
- implemented;
- locally tested;
- testnet tested;
- Base mainnet deployed;
- mainnet transaction verified;
- deployed browser verified;
- background automation verified.

Never collapse these into “done.”

## 15. Every real bug gets a regression test when reasonable
A browser/mainnet bug must not be fixed only by hand if it can be reproduced in test code.

## 16. No scope creep
Do not add AI recommendations, lending, social features, extra chains, complex branching, notifications, analytics dashboards, or unrelated integrations until the PRD's required mainnet loop is complete.

## 17. No provider swapping for convenience
Do not replace Base, official B20 assets, Chainlink total-return feeds, 0x, the bounded vault architecture, or the FastAPI worker without verified evidence that the locked path cannot satisfy the required outcome.

## 18. Never trust agent reports alone
When another coding agent says a milestone is complete:
- inspect the actual diff;
- inspect the relevant files;
- run/inspect relevant tests;
- verify real provider/mainnet evidence;
- confirm deployment status.

Test counts alone are not proof.

## 19. Protect already-working areas
A worker fix does not redesign the frontend. A frontend task does not rewrite contracts. A deployment fix does not reopen product scope.

## 20. One complete path beats five half-features
Submission priority:

`build rule → fund → activate → browser closes → real condition → real B20 trade → next step → evidence`

Anything not serving that loop is secondary.

## 21. Demo architecture is binding
A judge must quickly understand:
- stock;
- condition;
- action;
- next action;
- max capital;
- activate;
- evidence that it continued unattended.

Do not lead with contract vocabulary.

## 22. Final freeze
Once blockers B1–B12 in `PRD.md` pass:
- stop adding product features;
- audit README/docs;
- record demo;
- post on X;
- submit form;
- freeze the exact final commit SHA.

After submission, rotate/remove plaintext development secrets from local working environments as appropriate.
